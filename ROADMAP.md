Update the checkboxes and the status section as work lands.

## How we work

- Claude writes, Mike reviews. Each item is a small, reviewable commit with a short note
  on the Spring/JPA idea behind it.
- Commits are authored by Mike only. No co-author trailers or tool attribution.
- Tests cover what matters: the core user flows, ownership and visibility rules, and the
  migrations. No coverage targets, no tests for getters or trivial mapping.
- One branch per phase (or per larger item), merged to `main` when green.

## MVP definition

A person can sign up, search movies and TV shows, build watchlists, track status and
rating for each title, and see posters. It is deployed at a public URL.

Out of the first cut: reviews, public profiles, recommendations, legacy import/export.
Their old pages were removed in the redesign and are rebuilt in Phases 5 and 6.

## Phase 1: Make the core work (backend correctness) — done

Run the tests with `mvn test` in `backend/` (Docker must be running).

### 1.1 Test harness

- [x] `IntegrationTest` base class: one shared Testcontainers Postgres, Flyway on, so V1
      to V3 run for real. TMDB is always a mock. Replaced the H2 `contextLoads` test.
- [x] `AuthFlowTest`: register, login, `/me`, bad password, duplicate email, missing or
      short password, no token.
- [x] `WatchlistFlowTest`: create list, add title, list mine, get one, update item,
      remove item, delete list; duplicate title; invalid rating.
- [x] `WatchlistAccessTest`: private vs public lists; a stranger cannot change my list;
      an item cannot be changed through a different list; no email on public profiles.
- [x] `MovieImportTest`: movie and TV import with TMDB stubbed; same title twice reuses
      the row; a movie and a show may share a TMDB id.
- [x] `ReadEndpointsTest`: one pass over the read endpoints that used to return 500
      (reviews, recommendations, export/import) plus JSON errors for bad input.

Testcontainers was bumped from 1.20.3 to 1.21.4; the older version cannot talk to
Docker 29.

### 1.2 Lazy loading outside a transaction (9 endpoints)

Symptom was `LazyInitializationException` on list/get watchlists, public watchlists,
`/api/movies/popular`, `/api/recommendations`, the three review lists, `/api/me/export`.

Idea: a JPA collection like `Watchlist.items` or `Movie.genres` is loaded on first
access, and that needs an open database session. With `open-in-view: false` the session
closes when the transaction ends, so reads must happen inside one.

- [x] Read methods are transactional: `@Transactional(readOnly = true)` on
      `WatchlistService`, `ReviewService` and the two new services; write methods keep
      their own `@Transactional`. `MovieService.search` is deliberately left out so a
      slow TMDB call does not hold a database connection.
- [x] Query logic moved out of `RecommendationController` and `MeController` into
      `RecommendationService` and `LegacyWatchlistService`. Controllers no longer touch
      entities.
- [x] Avoid one query per row: `hibernate.default_batch_fetch_size: 50` in
      `application.yml`. Measured on 3 lists of 12 titles: `GET /api/watchlists` went
      from 42 queries to 5. (Chosen over `@EntityGraph` because it covers every read
      path with one setting.)

### 1.3 Adding a title failed (2 endpoints)

Symptom was `NonUniqueObjectException` on `POST /api/watchlists/{id}/items` and on
legacy import.

Idea: entities set their own UUID in the constructor. Spring Data decides "new or
existing?" by whether the id is null, so it treated every new entity as existing and
called `merge`, which makes a second copy. `addItem` also added the item to the
watchlist's collection, which saved the original on commit. Two objects, one id.

- [x] Ids are generated by Hibernate (`@GeneratedValue(strategy = GenerationType.UUID)`)
      on `User`, `Movie`, `Watchlist`, `WatchlistItem`, `Review`. No schema change.
      `Genre` keeps its assigned id because that id is TMDB's.
- [x] `Watchlist.addItem` / `removeItem` keep the list and its items in step; the
      service saves each new item once.

### 1.4 Security and privacy

- [x] Cross-user delete: items are now looked up by item id and list id together
      (`requireItem`), for delete as well as update; 404 otherwise.
- [x] Email leak: `GET /api/users/{id}` returns `PublicUserResponse` (id, display
      name). Email is only in `/api/auth/me` and the login/register responses.
- [x] Registration with a missing password is a 400. Password length is 8 to 72 (bcrypt
      ignores anything past 72 bytes).

### 1.5 Error responses

- [x] `GlobalExceptionHandler` extends Spring's `ResponseEntityExceptionHandler`, so
      malformed JSON, a non-UUID in the URL and similar keep their correct 4xx status
      and use the same JSON error shape. Unexpected exceptions are logged with a stack
      trace and return a generic 500.
- [x] Database constraint violations return 409.

Not done here, moved to Phase 3: a 401 from the security filter still has an empty
body, because it is produced before the request reaches the exception handler.

## Phase 2: Redesign and MVP frontend — done

The frontend was rebuilt rather than patched. Design: `docs/design-direction.html`
(also at https://claude.ai/artifact/VapZxjRCwT9ebWf7VZ9vdX).

### 2.1 Stack and design

- [x] Mantine 9 for components, replacing Tailwind. This needed React 19.
- [x] Theme in `frontend/lib/theme.ts`: dark by default with a light toggle, amber
      accent, a condensed heading font, separate colours for the four statuses.
- [x] TanStack Query for all server data (`frontend/lib/queries.ts`), so every page has
      the same loading, empty and error states.
- [x] One place for "401 means logged out": `api()` in `frontend/lib/api.ts` clears the
      session, and `useRequireAuth` sends the user to login and back.
- [x] Removed `react-hook-form` and `zod`; forms use Mantine's form package.

### 2.2 Pages

- [x] Header on every page: wordmark, search box, scheme toggle, account menu.
- [x] `/` home. Signed out: a short landing page with search and sign-up. Signed in:
      "Watching now", then lists as cards with posters and progress, with an empty state
      for a new account.
- [x] `/search`: poster grid, All / Movies / TV filter, paging. The plus button opens a
      menu of your lists (or makes a new one) and confirms with a toast; titles already
      on a list show a tick.
- [x] `/lists/[id]`: status filter with counts, sort, and a side panel for the selected
      title (status, rating, notes, remove). On a phone the panel is a bottom sheet.
      Edit details and delete list sit behind the options menu. A public list is
      read-only for everyone but its owner.
- [x] `/titles/[id]`: backdrop, poster, facts, genres, "Add to list", and which of your
      lists it is on.
- [x] `/login`, `/register`: field-level validation, server errors shown in place,
      return to the page you came from.
- [x] `/about`: restyled, TMDB attribution kept. The TMDB notice is in the footer of
      every page.
- [x] The three dynamic pages that were broken on Next 16 no longer exist; the new ones
      read the route id with `useParams()`.

### 2.3 Backend additions for the design

- [x] `backdropPath` on titles; `addedAt` on list items, which come back newest first.
- [x] `POSTGRES_HOST_PORT` in `docker-compose.yml`, so the database port can be moved
      when 5432 is taken.

Checked by hand in a production build against real TMDB data: sign-up, login, search,
add to list, the list panel, edit, remove, delete, the signed-out view of a public list,
the light scheme, and phone width. There are no automated frontend tests yet.

## Phase 3: Hardening before it is public — done

- [x] Refuse to start with the default `JWT_SECRET` when `SPRING_PROFILES_ACTIVE=prod`.
- [x] Session length: a login now lasts 7 days (`JWT_EXPIRATION_MINUTES`), up from 120
      minutes. Chosen over refresh tokens for simplicity. The trade-off: a stolen token
      works for up to 7 days and cannot be revoked; refresh tokens would fix that later.
- [x] Rate-limit login and register: 10 a minute per IP (`RateLimitFilter`), returns 429.
- [x] Search is limited to 30 a minute per IP, and TMDB results are cached in memory for
      5 minutes (`SearchCache`, `app.tmdb.search-cache-seconds`), so repeated searches
      and paging back and forth do not spend TMDB requests.
      Background: `GET /api/movies/search` is public and every call goes to TMDB through one shared
      4-requests-per-second gate, so one visitor can starve everyone. Require login, or
      limit per IP, and cache recent searches briefly.
- [x] A malformed date from TMDB is treated as unknown instead of causing a 500.
- [x] 401 responses have the same JSON error body as other errors.
- [x] `importTmdb` and `get` no longer call TMDB inside a database transaction: they
      read, call TMDB with no connection held, then write (`MovieService`). The nightly
      cache job still refreshes inside its own transaction; it runs in the background.
- [x] Search returns `{ results, page, totalPages }`, and the UI shows "Page 2 of 7" and
      disables Next on the last page.
- [x] Frontend tests with Vitest and Testing Library (`npm test` in `frontend/`, also run
      in CI): the API client (token, 401 sign-out, error mapping), the add-to-list menu,
      the login and sign-up form, and the list-matching helpers. The list page's side
      panel is not covered yet.
- [x] Swagger UI and the API docs are off under the `prod` profile (`application-prod.yml`).
- [x] CI uses `npm ci` with the lockfile. Still to confirm on the first push: the
      Testcontainers tests run in GitHub Actions.

## Phase 4: Deploy

- [ ] Pick hosting. `infra/README.md` assumes AWS (Amplify, App Runner, RDS), which has
      a monthly cost even when idle. Compare with a cheaper setup (for example a small
      container host plus managed Postgres plus static/Next hosting) before committing.
- [ ] Set `SPRING_PROFILES_ACTIVE=prod`, and configure forwarded headers so the rate
      limiter sees the visitor's IP rather than the proxy's.
- [ ] Production config: profile, secrets, CORS origin, Flyway on deploy, health check.
- [ ] The frontend Dockerfile runs `next start`, which Next warns about when
      `output: "standalone"` is set. Run the standalone server instead.
- [ ] Build and deploy from CI on merge to `main`.
- [ ] TMDB attribution visible in production (logo and notice are already in place).
- [ ] README: screenshots, live link, how to run.

**MVP is done here.**

## Phase 5: Features held back from the MVP

- [ ] Reviews: build the screens (write, edit, delete, show on the title page).
- [ ] Public profiles, and a "copy link" control on public lists.
- [ ] Theme options: let a user pick the accent colour (amber, teal, red, as in the
      design mockup's switch) and remember it.
- [ ] Legacy import/export UI. Import currently creates a new row per title; match
      against TMDB instead so imports do not duplicate.
- [ ] Filter and sort by genre, year, rating.
- [ ] Pagination on list endpoints.

## Phase 6: Recommendations and ML

Today "recommendations" is the 20 most popular titles already in the database minus
what you have added, so a fresh database shows nothing.

- [ ] Bring back a recommendations page ("Picks") once there is something to show.
- [ ] Seed a catalogue: import TMDB popular and top-rated lists on a schedule, within
      the existing cache rules.
- [ ] Step 1, no ML: weight genres by the user's ratings and watched history.
- [ ] Step 2, content-based: embed title overviews, store in pgvector, "more like
      this" and "because you liked X". Reuse the retrieval approach from GtHired.
- [ ] Step 3, collaborative filtering: train on MovieLens (maps to TMDB ids), since one
      user's data is not enough. Evaluate offline before shipping.
